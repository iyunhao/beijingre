# 北京二手房网签统计（网页版）

统计**北京每天二手房（存量房）网签量**的网页应用：月度日历、成交走势、月度对比，另含**期房 / 现房网上签约**观察视图（每个 tab 各有期房 / 现房 / 总计三张日历）与**独立数据校验报告**，支持深色模式与手机/桌面自适应。

数据来自 **北京市住房和城乡建设委员会**（存量房网上签约统计 + 房地产数据主题服务），服务端每天定时抓取入库、历史逐日累积。

**四个口径 tab**

| tab | 内容 |
| --- | --- |
| 存量房 · 网上签约套数 | 全部存量房（含住宅、商业、办公等） |
| 存量房 · 住宅签约套数 | 存量房住宅类（与住建委月报一致） |
| 期房 / 现房 · 网上签约 | 新建商品房当日两套序列（总套数） |
| 期房 / 现房 · 住宅签约 | 新建商品房当日两套序列（住宅套数） |

也可用 `?metric=total|residential|qfXfTotal|qfXfResidential` 直达任一视图。

## 功能

| 模块 | 说明 |
| --- | --- |
| **核心指标** | 本月累计、最新一日（含较前日涨跌）、近 30 日累计（「预估本月」已按需求下线） |
| **月度日历** | 每日成交套数 + 较上一交易日涨跌（涨红跌绿），鼠标悬停看当日明细；**历史周末只居中显示「周六+周日合计」**（实际值），不再展示两个推测单日数 |
| **成交走势** | 近 7 / 15 / 30 / 90 日柱状图 + 走势折线，悬停显示数值 |
| **月度对比** | 近 6 个月累计，本年与去年同期双柱对比，柱下标同比涨跌幅 |
| **链家签约** | 链家月度签约套数柱状图 + 市占率折线（占全市网签总量） |
| **期房 / 现房视图** | 最新一日 KPI、**三张月历（期房 / 现房 / 总计，共用月份导航 + 有数据月份跳转）**、已采集单日柱状图、逐日明细表；历史曲线缺失原因单独说明 |
| **数据质量与校验** | 逐月与官方月报对账表（合计 / 官方 / 偏差 / 校验结论）、缺口清单、口径说明 |
| **独立数据校验报告** | 四个 tab 常驻；重抓权威源站逐条比对的 **8 项硬校验**（PASS/FAIL）+ 2 项「如实披露」，明确区分「100% 正确」与「公开渠道不可确知」 |
| **每日自动刷新** | 服务端 30 分钟轮询 + 每天北京时间 09:05 / 22:05 强制刷新 + 数据过期时的请求兜底；前端每 10 分钟及切回前台时重拉 |
| **主题** | 跟随系统深浅色，也可手动切换（记忆在本地） |
| **响应式** | 桌面双栏、平板单栏、手机紧凑布局 |

## 快速开始

```bash
cd server
npm start          # 默认 http://localhost:3000
```

打开浏览器访问 `http://localhost:3000` 即可。

首次启动会自动载入 `data/seed.json`，之后按下列策略自动刷新（**默认开启，不需要外部 cron**）：

| 触发 | 时机 |
| --- | --- |
| 启动延时刷新 | 进程启动 5 秒后 |
| 常规轮询 | 每 30 分钟（默认） |
| 每日强制刷新 | 北京时间 **09:05 / 22:05**（`DAILY_REFRESH_TIMES` 可改，逗号分隔） |
| 兜底刷新 | 任意 `/api/` 请求发现 `meta.updatedAt` 超过 1 小时，后台补一次 |
| 前端重拉 | 每 10 分钟 + 页面从后台切回前台 |

刷新有并发锁与 5 分钟最小间隔保护；`/api/health` 的 `refresh` 字段可查看最近一次触发原因与结果。

环境变量：`PORT`、`HOST`、`AUTO_SCRAPE=0`（关闭自动抓取）、`SCRAPE_INTERVAL_MS`、`DAILY_REFRESH_TIMES`、`REFRESH_STALE_MS`、`REFRESH_TOKEN`。

手动刷新仍然可用：`npm run fetch`（抓一次就退出，适合外部 cron）。执行后如需同步静态快照与冷启动种子，再跑：

```bash
npm run verify      # 重抓权威源站，逐条核对并生成 data/verification.json
npm run web:data    # 重新生成 web/data/snapshot.js（含校验报告）
npm run seed        # 重新生成 server/data/seed.json
```

> `npm run verify` 不改动任何业务数据，只重新抓取住建委存量房公示页 / 房地产数据主题服务页 / 北京房市儿原始日序列，与本地库逐条比对后写报告。任一项硬校验不通过即以非零退出码结束，便于接 CI 告警。

### 纯静态部署（不要后端）

`web/` 是纯静态目录，直接丢到任意静态托管（Nginx / GitHub Pages / Vercel / OSS）即可：

- 页面会先请求 `/api/days`，失败则自动回落到 `web/data/snapshot.js` 内置快照；
- 直接双击 `web/index.html`（`file://`）也能打开；
- 想更新数据，先跑一次抓取再重新导出快照：

```bash
cd server
npm run fetch          # 抓最新数据
npm run web:data       # 重新生成 web/data/snapshot.js
```


只跑 API、抓取交给系统定时任务：

```bash
# crontab -e   每天 09:30 / 14:30 / 20:30 各抓一次
30 9,14,20 * * * cd /opt/bj-ershoufang/server && AUTO_SCRAPE=0 /usr/bin/node scripts/fetch-once.js >> /var/log/bj-fetch.log 2>&1
```

Nginx 反代：

```nginx
server {
  listen 80;
  server_name bj.example.com;
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
  }
}
```

> 抓取会累积历史，服务上线越早、日序列越完整。`seed.json` 已内置 **364 天（2025-11-10 ~ 2026-11-08）**存量房回溯数据 + 9 天期房/现房锚点用于冷启动。`store.json` 被 `.gitignore` 忽略，重新部署前记得跑 `npm run seed` 与 `npm run web:data`。

### 在线分享链接与自定义域名（重要）

通过 WorkBuddy「发布为应用」分享时，平台分配的是形如 `<随机 id>.sg2.agentos-app.run` 的**平台子域名**，不是自有域名：

| 需求 | 是否支持 |
| --- | --- |
| 把链接改成 `www.housingdataforyun.com` 这类**任意自有域名** | **不支持**。发布能力没有自定义域名绑定 / DNS / CNAME 配置项 |
| 让链接前缀更好记（例如 `housingdataforyun.sg2.agentos-app.run`） | 部署参数 `domainPrefix` 只能在**首次创建新应用**时指定子域名第一段；已有应用重新发布会沿用原链接，该参数被忽略，且同一个目录不能再创建第二个应用 |
| 重新发布会换链接吗 | 通常沿用同一个 `appId` 的链接；但平台沙箱重分配时可能给出新链接（本项目发生过一次），旧链接随即失效 |

`housingdataforyun.com` 经 WHOIS 查询当前**未注册**，`dig` 查不到 NS / A 记录。若确实需要该域名，正确路径是：

1. 注册并持有该域名，取得 DNS 管理权；
2. 准备 HTTPS 证书；
3. 二选一：
   - 把本项目部署到**支持自定义域名绑定**的托管平台（Vercel / Netlify / 自有服务器 + Nginx，见上文反代配置），在平台侧绑定域名并把 `www` CNAME / A 记录指过去；
   - 或者保留现有分享链接作为源站，用 Cloudflare / 自建 Nginx 做**反向代理**，把 `www.housingdataforyun.com` 转发到平台链接。

注意本项目含 Node 后端与自动抓取：若改用纯静态托管，只能放 `web/`，此时页面会回落到 `web/data/snapshot.js` 内置快照，需要靠 `npm run fetch && npm run web:data` 定期重新导出；要保留每日自动刷新就必须跑 Node 服务。

| 接口 | 说明 |
| --- | --- |

| `GET /api/months` | 有数据的月份列表 |
| `GET /api/quality` | **数据质量报告**：覆盖区间、各质量层级计数、缺口清单、逐月对账表 |

| `GET /api/snapshot` | 一次性导出完整快照（含 `newHomes`、`verification`），供离线/调试 |
| `GET /api/refresh?token=` | 手动触发抓取（设 `REFRESH_TOKEN` 后需带 token） |

## 数据口径

| 指标 | 说明 |
| --- | --- |
| 主指标 | **住宅签约套数**（二手房住宅类网签），日序列最完整 |
| 备选指标 | 网上签约总套数（含非住宅），`?metric=total` |
| 本月累计 | 有官方月报时以**官方月报**为准（权威口径）；无月报时为当月逐日加总 |
| 涨 / 降 | 该日相对**上一个有数据日**的套数变化 |

### 质量分级（每日数据都带 `quality` 字段）

| 标记 | 含义 | 数量（2026-11-08） |
| --- | --- | --- |
| `official` | 住建委官方页当日直接公布、未被重建覆盖 | 3 |
| `exact` | 逐日序列中的工作日原值，**未做任何修改** | 243 |
| `derived` | 周末值，由周合计减工作日合计反推（合计精确、内部分配近似） | 102 |
| `estimated` | 上游整段缺失或节假日 / 调休的缺口回补（估算） | 16 |

日历中估算日有虚线下划线、悬停明确标注；前端不会把推算值伪装成披露值。

**历史周末的展示规则（与需求一致）**：官方逐日历史值无法回补，能确知的只有「周六 + 周日合计」（周合计 − 该周工作日之和）。因此日历把未知拆分的历史周末两格**合并成一格、居中只列合计（实际数字）**，不再显示两个推测单日数；跨月的周末在相邻两个月各显示一次并标注「跨月」。服务端仍保留内部拆分值用于月合计与图表对账，但**界面不对外展示**。

从逐日直采开始，官方给出某一天实际值后，另一天可由「周合计 − 工作日 − 官方日」精确反推，这两天单日值都确知，日历会**各自单列**（标记「官方直采」/「周合计精确反推」），不再合并。例如 2026-11-07 = 218（精确反推）、2026-11-08 = 118（官方直采）。

### 周末数据到底从哪来（重要更正）

**结论：住建委官方页每天都发布数据，包括周六、周日。** 之前以为「周末不网签」是被第三方图表误导了。

证据（Wayback 快照，四个不同星期）：

| 快照时间 | 星期 | 页面显示日期 | 住宅套数 |
| --- | --- | --- | --- |
| 2022-05-21 13:57 | 周六 | 2022/5/20（周五） | 373 |
| **2022-10-24 12:02** | **周一** | **2022/10/23（周日）** | **85** |
| 2025-08-08 03:04 | 周五 | 2025/8/7（周四） | 515 |
| 2026-05-20 08:21 | 周三 | 2026/5/19（周二） | 707 |

周日有 85 套，是真实网签量。页面**一次只显示最新一天**、延迟约 1~2 天，所以周六下午还停在周五，周一看得到周日。

那为什么房市儿的日曲线没有周末？因为它**主动把周末过滤掉了**（只画工作日），但计算周合计时又把周末算进去了。这才是「周末无数据」错觉的根源。

**对我们的影响**

| 时段 | 周末数据来源 | 界面展示 | 质量 |
| --- | --- | --- | --- |
| 过去（2025-11-10 ~ 逐日直采开始前） | 官方逐日值已无法回补，用「周合计 − 该周工作日」精确反推 | **只显示周六+周日合计**（一格居中） | 合计精确，周六/周日拆分不可确知 |
| 现在起 | 每天 09:05 / 22:05 及 30 分钟轮询抓取官方页，含周末 | 两天各自单列 | `quality:'official'` 真实值 / 精确反推 |

也就是说：**推算只是历史遗留问题，会随每天抓取自动减少。** `meta.capture` 记录实际采到过哪些日期，漏采会在质量面板告警。

反推的周末合计经第三方交叉验证：冰山指数同期周末合计为 19 / 911 / 268，与本方法结果**分毫不差**（差异只在周六/周日的内部分配：冰山 4/15、718/193、190/78，我们按比例拆分）。


当前对账结果：**10 个有官方月报的月份全部校准到 0.00% 偏差**（2026-01 ~ 2026-10）。2026-04 / 2026-05 上游日序列曾缺 16 个工作日，现以「节假日 / 调休 + 中位模式」回补并标记 `estimated`，月合计仍能闭合；回补日单独打标、不冒充披露值。

### 数据覆盖范围（重要）

| 项 | 实际情况 |
| --- | --- |
| 可回溯区间 | **2025-11-10 → 2026-11-08，共 364 天** |
| 是否够 24 个月 | **不够**。24 个月需回溯到 2024-11 前后，公开渠道拿不到 |
| 为什么 | 住建委公示页无历史日期参数（`?date=` / `?startDate=` 均无效，只显示最新一日 + 上一个完整月）；房市儿日序列上限 1 年；Wayback Machine 对 2024–2026 无连续快照；冰山指数为 Nuxt 单页应用、接口返回 429，无公开 API |
| 缺口 | 上游缺失的 16 天已用节假日/调休 + 中位模式估算回补并标记 `estimated`；日历与质量面板均可查，未做线性插值凑数 |

**未做的事**：没有编造、没有线性插值、没有用「日均 × 天数」凑数。缺就是缺，页面和 API 都会显式列出。

### 独立校验与「100% 正确」的边界

`npm run verify`（`server/scripts/verify-data.js`）**不信任 `store.json` 的自述**：重新抓取三个权威源站，逐条与本地库比对，结果写入 `server/data/verification.json`，经 `/api/verification`、网页「独立数据校验报告」面板（四个 tab 常驻）与 `web/data/snapshot.js` 对外展示。任一项硬校验失败即整体 `FAIL` 并以非零退出码结束。

**8 项硬校验**（当前结果 `PASS 8/8`）：

| 校验 | 结果 |
| --- | --- |
| 工作日单日值 vs 源站原始日序列 | 245 / 245 逐条相同，0 处不符、0 缺失 |
| 官方最新一日 vs 住建委公示页 | 2026-11-08 住宅 116 / 总量 118 一致 |
| 逐日住宅合计 vs 官方月报 | 10 个月全部偏差 0 |
| 逐日网上签约总套数 vs 官方月报 | 2026-10 总量 14499 逐日加总分毫不差 |
| 期房/现房当日值 + 内部一致性 | 9 条记录合法，最新日四字段与官方一致 |
| 数值与结构不变量 | 364 天，无负数 / 非整数 / 总量<住宅 / 重复 / 缺质量标记 |
| 官方月报锚点表 vs 实时月报 + 历史存档 | 2026-10 住宅 13081 / 总量 14499 一致；另核对 4 个存档月报，0 处不一致 |
| 历史周末「两天合计」vs 源站周合计精确反推 | 26 个源站自洽周逐一验证，全部相等（偏差 0） |

**2 项如实披露（不参与「准确」宣称）**：

- 源站周序列 vs 官方月序列本身存在小幅口径差：48 周中 26 周完全一致、19 周微差（最大 1.05% / 26 套）、3 周为错值周或源站整段缺口。本站以住建委官方月报为硬约束做极小校准，月合计因此始终 0.00% 一致；校准幅度在报告里逐周列出。
- 公开渠道**根本不存在**的数字：历史周六 / 周日**各自**的单日值（界面只显示两天合计）、16 天源站整段缺口回补（估算，日历标「缺口回补」）、期房/现房历史逐日值（仅 9 个零散存档日）。

> 换句话说：**能 100% 确证的数字全部逐条列在报告里，不能确证的也全部列出来并明确标注**，不存在「看起来精确但其实是猜的」数字。想让历史周末单日值也变成 100% 精确，唯一途径是从现在起持续逐日直采（时间换数据），公开历史源无法回补。

### 期房 / 现房数据（新增两个 tab）

来源：住建委「房地产数据主题服务」页 `http://bjjs.zjw.beijing.gov.cn/eportal/ui?pageId=307749`，每天给出**最新一天**的两张表：

```text
YYYY/M/D 期房网上签约   套数 / 面积 / 住宅套数 / 住宅面积
YYYY/M/D 现房网上签约   套数 / 面积 / 住宅套数 / 住宅面积
```

例如 2026/11/8：期房 307 套（住宅 220）、现房 33 套（住宅 21）。

**为什么没有完整历史曲线**：该页只公示最新一天；历史逐日查询接口 `popup_everyday_all.asp` / `popup_everyday_ys.asp` 已下线（404），Wayback 也无快照。另找过 房市儿（无新房页）、几套房（仅工作日存量房）、ershoufangdata API（仅最新 3 个工作日 + 月累计），均无连续历史。因此：

- `server/data/newhomes-archive.json` 保存了 **9 个**从 Wayback 快照摘出的单日锚点（2020-01-14 ~ 2026-11-08），冷启动时幂等播种；
- 从本版本起**每天直采并逐日累积**，曲线会随时间自然变长；
- 存档锚点单独标注来源，不与实时直采数据混淆；表格按日期倒序，明确写着「日期不连续」。

数据存在独立的 `db.newHomes`（扁平字段 `qfTotal` / `xfTotal` / `qfResidential` / `xfResidential` 及四个面积字段），不与存量房 `db.days` 混用。

**三张月历**：两个期房/现房 tab 各有「期房 / 现房 / 总计（期房 + 现房）」三张日历，共用一个月份导航（可按日历月前后翻），另有下拉框可**直接跳到有采集数据的月份**（当前 9 个月），避免在数据稀疏的年份里逐月空翻。

- 只把**已采集到的官方单日实际值**放进对应日期格：不插值、不按日均凑数；空白格显示「–」代表**未采集，不是 0**；
- 每格标注来源（`实时抓取` / `存档锚点`），悬停给出日期、数值、来源与「较本月上一采集日」的涨跌；涨跌只在同月存在 ≥2 个采集日时才计算；
- 三张日历右下角「合计」只是**本月已采集这几天的加总**，不等于整月网签量，页面有醒目提示，不能与存量房月累计直接对比；
- 「总计」日历在当日缺少期房或现房任一侧数据时不给出总计（不拿单边值冒充合计）。

本站日序列只覆盖 2025-10-23 起，做不了「去年同月」的自动推导，因此去年同月的**住宅签约套数**单独存档在 `server/data/external.json`，逐条标注出处：

| 月份 | 住宅网签 | 来源 |

| 2025-05 | 14,277 | 北京链家研究院（北京市住建委数据） |

| 2025-07 | 12,784 | 北京链家研究院（与 8 月环比 547 套反推一致） |

**交叉验证**：用这批数据算出的同比，与今年各月报道的同比口径完全吻合 —— 2026-05 +11.9%（报道「约 12%」）、2026-06 +9.8%（报道「9.8%」）、2026-08 +3.9%（报道「约 3.9%」）。说明这组数据可信。

当月未结束时只显示累计值，不给同比柱，避免「拿半个月比整月」的误读。

### 链家签约套数与市占率

来源：住建委「房地产数据主题服务」页（`pageId=307749`）里的**存量房网上签约月统计 · 按经纪机构**。

- 该页**只保留最新一个月的机构排行**（当前为 2026-09，链家 8,218 套）。
- 历史月份靠 Wayback 快照补齐（2025-07、2025-10、2026-04、2026-06），之后由爬虫按月自动累积，因此图表月份暂时不连续。
- **市占率 = 链家签约套数 ÷ 全市网上签约总套数**。这个口径是试出来的：用「全市住宅」做分母会算出 47%~53% 的跳变，用「全市总套数」则是 41.6% → 42.5% → 42.6% → 47.4% → 46.6%，走势平稳且符合行业认知，故采用后者。



冰山指数（原 `bingshandashu.com`，现跳转 `bingshanai.com`）展示的周末值与我们的反推结果**周末合计完全一致**，说明双方用的是同一套周汇总口径。它本身是 Nuxt 单页应用、接口返回 429、无公开 API 文档，抓不了；但它也不需要抓——它的数据源就是住建委官方页的每日发布，而这个页面我们自己每 30 分钟就在采。

换句话说：**没有神秘的第三方源，源就是住建委官方页。** 冰山只是把「每天换一天的页面」持续抄了下来。

## 常见问题

**Q：页面打开是空的 / 只有快照数据？**
A：说明 `/api/days` 没通。检查后端是否启动、反代是否正确；纯静态托管下这是预期行为，更新数据用 `npm run fetch && npm run web:data`。

**Q：为什么只有 364 天，不能回溯 24 个月吗？**
A：公开渠道的硬上限就是一年左右，原因见上文「数据覆盖范围」。要更长历史只有两条路：① 从 2025-11 起持续累积（时间换数据，一年后自然到两年）；② 有付费数据源（中指、贝壳研究院等）提供历史日序列，替换 `server/src/rebuild.js` 的输入即可。

**Q：为什么历史周末只有一格数字，不是周六、周日各一个？**
A：因为官方历史逐日值无法回补，**能确知的只有「周六 + 周日合计」**（周合计 − 该周工作日之和），周六/周日各占多少并不知道。所以日历把这两天合并成一格、居中只列合计（实际数字），不再展示两个推测单日数；跨月周末在相邻两月各显示一次并标「跨月」。从逐日直采开始，官方给出了某一天实际值，另一天可由减法精确反推，两天就各自单列了。

**Q：周末的合计可信吗？**
A：周末**合计**来自「周合计 − 工作日合计」的精确减法，不是估算，并且与冰山指数同期数字完全一致（19 / 911 / 268）；整体再用官方月报校验，10 个有月报的月份全部闭合到 0.00%。内部 0.70 拆分只用于服务端月合计/图表对账，**界面不展示**。另外，官方页每天都发布周末数据，所以**从现在起新增的周末都是真实值**。

**Q：期房 / 现房为什么只有 9 天数据？**
A：住建委只公示最新一天，历史查询接口已下线。本站从本版本起每天直采累积，日期不连续是数据源限制，不是抓取失败；详见上文「期房 / 现房数据」。

**Q：三张日历里大片空白格是什么意思？右下角「合计」能当整月数据用吗？**
A：空白格 = **未采集**，不是 0。「合计」只是本月已采集到那几天的加总，**不是整月网签量**，不能与存量房月累计对比。想快速找到有数据的月份，用日历上方的「跳到有数据的月份」下拉框。

**Q：数字真的 100% 正确吗？怎么核对？**
A：跑 `npm run verify`，或看页面底部「独立数据校验报告」。当前 **8/8 项硬校验通过**：245 个工作日单日值逐条与源站一致、官方直采日一致、10 个官方月报月份的逐日合计（两个口径）偏差 0、官方月报锚点表一致、26 个自洽周的历史周末两天合计逐周反推偏差 0、期房/现房当日值一致、全部数值合法。**但公开渠道根本不存在的数字不会被冒充成精确值**：历史周六/周日各自的单日值、16 天缺口回补估算、期房/现房历史逐日值，都在报告里列为「不可确知」并在界面隐藏或标注。源站周/月序列自身的口径微差（最大 1.05%）也逐周披露。

**Q：能把分享链接改成 `www.housingdataforyun.com` 吗？**
A：当前发布能力**做不到**，它只分配平台子域名，没有自定义域名绑定。该域名目前未注册、无 DNS 记录。可行路径是先注册域名 + 取得 DNS 管理权 + HTTPS 证书，再把项目部署到支持自定义域名的托管平台，或用 Cloudflare / 自建 Nginx 反代到现有分享链接。详见「在线分享链接与自定义域名」。

**Q：数据多久更新一次？需要配 cron 吗？**
A：不需要。服务端默认 30 分钟轮询 + 每天北京时间 09:05 / 22:05 强制刷新 + 数据过期兜底，前端每 10 分钟重拉。`/api/health` 的 `refresh` 字段可查看状态；想用外部 cron 也可以跑 `npm run fetch`。

**Q：抓取失败怎么办？**
A：`/api/health` 的 `lastError` 会给出原因。抓取内置 `curl` 兜底（部分容器/代理环境里 Node 直连会超时）。若官方页面改版，调整 `src/parse.js` 的选择器。

**Q：想统计其他城市？**
A：把 `src/parse.js` 的 `SOURCES` 换成对应城市住建委的公示页，并调整 `parseOfficial` 的解析规则；前端只需改 `web/index.html` 的标题文案。

**Q：深色模式？**
A：默认跟随系统，右上角按钮可手动切换，也支持 `?theme=dark` / `?theme=light` 强制指定。
